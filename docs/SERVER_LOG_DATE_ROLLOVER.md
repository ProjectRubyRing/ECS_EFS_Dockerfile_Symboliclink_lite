# server.log が、日付をまたいだあとも前の日のファイルに書き続けられる理由

対象は JBoss EAP の `server.log` を、EFS 上の `mid/current` 経由でタスクごとに分けている構成である。
実装の出典は `docker/base/entrypoint.sh`（修正後）と、修正前の 2 段リンク
（`/opt/jboss-eap/standalone/log` → `.../mid/current`）である。
ローテーションの手順は JBoss Log Manager の `PeriodicRotatingFileHandler`
（2.1.19.Final と、2026 年時点の main ブランチ。時計の計算が `Calendar` から `java.time` に変わっても、閉じる・rename する・開き直すの 3 手は同じ）に基づく。

この文書は、先にたとえで全体を掴み、そのあとで同じことをファイルとファイルディスクリプタの言葉でたどる。

---

## 0. 先に結論

日付が変わったあとに `server.log.2026-09-16` へログが伸び続けるのは、JBoss が「前の日のファイルを選んで開いている」からではない。

起きていることは次の順番である。

1. 新しいタスクが `server.log` という名前の新しいページを作り、鉛筆（ファイルディスクリプタ）をそのページに刺す。
2. そのあと、まだ生きている古いタスクが日付ローテーションを実行する。
3. 古いタスクは、自分が刺しているページではなく、**その瞬間のパス**で `server.log` を `server.log.2026-09-16` という名前に付け替える。
4. 修正前のパスは共有の `current` を通る。`current` はすでに新しいタスクのディレクトリを指している。
5. 付け替わるのは、新しいタスクが開いたばかりの `server.log` である。
6. 新しいタスクの鉛筆は、名前が変わったあとも同じページに刺さったままである。以降の行は `server.log.2026-09-16` に増える。
7. 古いタスクはパスを開き直すので、新しいディレクトリに空の `server.log` を作り、日付をまたいだ自分のログをそこへ書く。

日中や夕方にタスクが複数になっても、**日付の境目をまたいで両方が生きているとき**にこの付け替えが起きる。境目の前は、古いタスクの鉛筆が古いディレクトリの `server.log` に刺さったままなので、ログは混ざらない。

起動のたびに `server.log-yyyy-MM-dd HH` というファイルが作られることは、EAP の標準設定では起きない。標準の suffix は `.yyyy-MM-dd` で、出来上がる名前は `server.log.2026-09-16` のようにドットで日付が付く。時間まで付く `server.log.2026-09-17-00` は、suffix を `.yyyy-MM-dd-HH` にしたときだけである。

対策は、デプロイの 100% / 200% をやめることではない。JBoss が開くパスと、日付ローテーションが rename するパスを、**そのコンテナが起動したときの実ディレクトリ**に固定する。`current` は「最後に起動したディレクトリを人間が見るための札」だけにする。

## 1. ノートでたとえる

クラスに 1 冊の共有ノートがあると思いがちだが、この構成はもう少し込み入っている。

| たとえ | システムの実体 |
|---|---|
| 中身が書いてある紙 | ファイルの実体（inode）。中身はここにある |
| 表紙に書いた名前 | ディレクトリエントリ。`server.log` や `server.log.2026-09-16` |
| 鉛筆を刺したままにすること | ファイルディスクリプタ（FD）。`open` したプロセスが持つ |
| 「いまのノート」と書いた札 | EFS 上のシンボリックリンク `mid/current` |
| 先生が日付の変わり目にやる作業 | `PeriodicRotatingFileHandler` の rollover |
| 新しい子が席に着く | ローリングデプロイで起動する新しい ECS タスク |
| 古い子がまだ席にいる | `minimumHealthyPercent=100`、`maximumPercent=200` のあいだ生きている旧タスク |

紙と表紙は別である。表紙の名前を書き換えても、すでに刺さっている鉛筆は同じ紙を指す。これは 1970 年代から Unix がそう作ってある。ログローテーションの事故のほとんどは、この 1 点から始まる。

修正前の教室では、先生も新しい子も「いまのノート」という札を見てからノートを開く。札は教室に 1 枚しかなく、後から来た子が札を自分の机へ向け替える。古い子の鉛筆は、刺したときの紙に残る。しかし古い子が日付の作業で「札の先の `server.log` という表紙を、昨日の日付の表紙に書き換える」と、書き換わるのは**いま札が指している机**、つまり新しい子のノートである。新しい子の鉛筆は、表紙が `server.log.2026-09-16` になった紙に刺さったままになる。

修正後は、各人の机の引出しに「自分のノートはここ」という個人の札を入れる。教室の共有札 `current` は、あとから来た人の机を示す案内だけになる。先生の日付作業は、自分の引出しの中だけで表紙を書き換える。

## 2. なぜこの形になったか

### 2.1 ファイル名と、開いたあとの鉛筆

Unix 第 7 版のころから、`open` はパスを一度だけ辿って、開いた実体に番号（FD）を付ける。そのあと `rename` で名前を変えても、FD の向き先は変わらない。`creat` で同じ名前の新しいファイルを作っても、古い FD は古い実体に書き続ける。

この性質は、動いているプロセスのログを消さずにファイルを世代へ送るために使われてきた。同時に、「ローテーションしたつもりが、プロセスは古い実体へ書き続けている」という障害の型にもなってきた。`logrotate` が `copytruncate` と「rename してからプロセスに開き直させる」を両方持っているのは、この型が 1990 年代にはすでに運用の中心問題だったからである。

### 2.2 Java のログが日付のファイル名を持ち始めたとき

Java の標準 `java.util.logging.FileHandler`（Java 1.4、2002 年）は、サイズと世代番号（`%g`）で回す。日付では回さない。

日付で回す慣行を広くしたのは Log4j 1.x の `DailyRollingFileAppender`（2001 年頃）である。パターン `'.'yyyy-MM-dd` で、日付が変わるとファイル名に日付を付ける。ここで「今開いているファイル」と「名前の付け替え」が分かれた。複数プロセスが同じパスを開くと、付け替えと FD がずれる。

### 2.3 JBoss が Log Manager を持った理由

JBoss AS 7 / EAP 6（2011〜2012 年）は、モジュールクラスローダの中で Log4j をサーバ全体のログに使うのをやめた。サーバ自身のログは JBoss Log Manager（`jboss-logmanager`）に移った。日次のハンドラが `PeriodicRotatingFileHandler` である。

suffix は `java.text.SimpleDateFormat`（新しい版では `DateTimeFormatter`）に渡せる文字列で、**いちばん細かい単位**がローテーションの間隔になる。

| suffix | 間隔 | 付く名前の例 |
|---|---|---|
| `.yyyy-MM-dd` | 日 | `server.log.2026-09-16` |
| `.yyyy-MM-dd-HH` | 時 | `server.log.2026-09-17-00` |
| `.yyyy-MM-dd-a` | 午前 / 午後 | `server.log.2026-09-17-AM` のような形 |

EAP の `standalone.xml` の初期値は `.yyyy-MM-dd` である。Red Hat の EAP 6.4 管理ガイド（文書サイト上の更新表示は 2026-09 でも、説明している仕様は当時から同じ）には、2014-10-20 に回ったファイルが `server.log.2014-10-19` になる、と書いてある。付く日付は「新しい日」ではなく、**いま閉じた期間**である。

2012 年 7 月の開発者フォーラムで、当時の実装は「サーバが日付をまたいで生きていないと回らない」と説明されている。その直後に、「ファイルの最終更新時刻を見て、期間が違えば次の書き込みで回す」へ変わった。今のソースは次の形である。

- `setFile` は、ファイルが既にあり `lastModified > 0` なら、その時刻から次の境目を計算する。このメソッドの中では rename しない。
- ファイルが無い、または時刻が 0 なら、今の時刻から次の境目を計算する。
- 実際の rename は `preWrite` で、ログレコードの時刻が境目以上になった最初の 1 行で走る。
- 1 行も出なければ、日付が変わってもファイル名は変わらない。

`rollOver` の 3 手は、2.1.19.Final でも main でも同じである。

1. `setFile(null)` で、**自分の**ストリームを閉じる。
2. `SuffixRotator.rotate` が `Files.move(パス, パス + nextSuffix, REPLACE_EXISTING)` を行う。
3. 元の `File` オブジェクトで `setFile` し、同じパスを開き直す。

`nextSuffix` は、境目を計算したときの「閉じる側の期間」をフォーマットした文字列である。9 月 16 日に起動して 9 月 17 日 0 時を境目にしているタスクの suffix は `.2026-09-16` になる。

`Files.move` は、パスの途中にあるディレクトリシンボリックリンクを、**呼んだ瞬間**に辿る。`server.log` 自体がシンボリックリンクである必要はない。親の `log` や `current` がシンボリックリンクなら、そのときの向き先で rename される。

開き直しも同じである。自分の FD は閉じたので、古いタスク自身は「名前が変わった紙」には書き続けない。書き続けるのは、**別のプロセスが、rename より前に同じ実体を開いていた場合**の、そちらの FD である。

### 2.4 ECS と EFS が、単体サーバには無かった共有を足した

Amazon ECS は 2014 年、EFS は 2015 年発表・2016 年一般提供である。EFS は POSIX の見た目を持つ共有ファイルシステムで、シンボリックリンクも FD のルールも、上に書いた Unix のままである。EFS が rename を壊しているのではない。rename の結果が、マウントしている全部のタスクから見える。

ローリングデプロイの `minimumHealthyPercent=100` と `maximumPercent=200` は、希望台数を割らずに新しいタスクを先に起動するための設定である。希望台数 1 なら、デプロイ中は旧 1 + 新 1 で 200% になる。新しいタスクが健全になったあと、古いタスクはロードバランサの登録解除（ALB の deregistration delay の初期値は 300 秒）を経て、SIGTERM、`stopTimeout`（初期値 30 秒、Fargate の上限は 120 秒）で止まる。日付の境目にこの重なりがかかると、両方の JVM が同時に生きる。

日中や夕方のデプロイ、スケールアウト、希望台数 2 以上も、同じ「複数タスクが同時に生きる」状態を作る。違いは、その時間に日付ローテーションの rename が走るかだけである。

### 2.5 このリポジトリが `current` を置いた理由

`readonlyRootFilesystem=true` のコンテナは、起動後にルートファイルシステムへ書けない。`/opt/jboss-eap/standalone/log` のシンボリックリンクはイメージを作るときにしか置けない。一方、タスクごとのディレクトリ名は起動するまで決まらない。

2026-07-21 の初回実装は、ビルド時に `standalone/log` → `.../mid/current` を焼き、起動時に EFS 上の `current` を ECS タスク ID へ向けた。タスク ID はメタデータエンドポイント v4 の `TaskARN` の末尾である。ローカルの `docker run` では取れない。

2026-07-22 の変更で、ディレクトリ名は `起動時刻(YYYYMMDDhhmmss)-ランダム英数字8桁` になった。メタデータに依存せず、同じ EFS を複数サービスが使っても名前が衝突しにくい。2 段リンクの形はそのまま残した。タスク ID 方式のスクリプトは `entrypoint.taskid.sh` に残したが、そこにはあとから入った configuration の復元が無かった。

設計メモには、すでに次の注意があった。`current` は最後に起動したタスクを指す。開いている FD は動かない。しかしローテーションで**新しく作るファイル**は、そのときの `current` の先に出来る。希望台数 1 なら実害は小さい、と書かれていた。

日付の境目のローリングデプロイは、その「新しく作るファイル」が `server.log` の reopen そのものになる瞬間である。希望台数 1 でも 100/200 のあいだはタスクが 2 つになる。実害が小さい、では済まない。

## 3. 修正前の経路

```
/opt/jboss-eap/standalone/log
        │  イメージに焼いたシンボリックリンク（全タスクで同じ文字列）
        ▼
.../mid/current
        │  EFS 上に 1 つ。最後に起動したタスクが ln -sfn で向け替える
        ▼
.../mid/<そのときの一意名>/server.log
```

`standalone.sh` は、`JBOSS_LOG_DIR` が空なら `JBOSS_HOME/standalone/log` を使う。この文字列は、Linux 版のスクリプトでは **環境変数のままでは `readlink` されない**。`JAVA_OPTS` の中に `-Djboss.server.log.dir=` があるときだけ、起動の瞬間に `readlink -m` で実体へ解決する。標準の起動では、JVM が覚えるパスはシンボリックリンクを含んだままである。

JBoss のログハンドラは `relative-to="jboss.server.log.dir"` で `server.log` を開く。覚えるのはこのパスである。FD は開いた瞬間の実体を指す。次にパスを使うのは、日付ローテーションの rename と reopen である。

## 4. 古いタスクの server.log は、日付の境目にどう回るか

ここでの「古いタスク」は、日付の境目より前に起動し、境目の時点でもまだ止まっていない JVM である。

### 4.1 境目の前

起動時にディレクトリは空である。ハンドラは `server.log` を作成して開く。`append` の初期値は true なので、同じ日に開き直しても追記になる。

`nextSuffix` は起動日、たとえば `.2026-09-16`。`nextRollover` は次の日の 0 時（JVM のタイムゾーン。コンテナが UTC なら日本時間の 9 時が境目になる）。

このあいだの書き込みは、開いたときの FD へ行く。`current` があとから別のディレクトリへ向いても、**この FD は動かない**。日中に新しいタスクが起動しても、古いタスクのログは古いディレクトリの `server.log` に伸びる。

### 4.2 境目のあとの最初の 1 行

ログレコードの時刻が `nextRollover` 以上になると、`rollOver` が走る。

1. 古いタスクは自分の FD を閉じる。古いディレクトリの紙への書き込みは、ここで止まる。
2. 覚えているパスで `server.log` を `server.log.2026-09-16` へ move する。
3. 同じパスで `server.log` を開き直す。中身は新しい空のファイルである。
4. `calcNextRollover(今)` により、次の suffix は `.2026-09-17`、次の境目は 9 月 18 日 0 時になる。

パスが自分の実ディレクトリだけを指していれば、これは正しい日次ローテーションである。

- `.../旧ディレクトリ/server.log.2026-09-16` … 9 月 16 日の内容
- `.../旧ディレクトリ/server.log` … 9 月 17 日 0 時以降の内容

パスが共有の `current` を通り、`current` がすでに新しいタスクを指していると、2 と 3 は**新しいディレクトリの中**で起きる。古いディレクトリの `server.log` は、FD を閉じただけで、名前は `server.log` のまま残る。昨日の内容は日付付きの名前にならない。

### 4.3 古いタスクは、前日付ファイルへ書き続けない

古いタスク自身は、rollover の前に自分の FD を閉じている。閉じたあとに書くのは、開き直したパスの新しい `server.log` である。

前日付ファイルへ書き続けるのは、rename の対象になった実体を、**別の JVM が開いたまま持っている**側である。今回の観測では、それが新しいタスクである。

## 5. 新しいタスクは、server.log をどう作り、FD をどう持つか

新しいタスクのエントリポイントは、起動の早い時点で次を行う。

1. `mid/<一意名>/` を作る。timestamp 方式なら `mkdir` が成功した名前だけを採用する。taskid 方式ならタスク ID のディレクトリを作り、同一タスクのコンテナ再起動では既存を再利用する。
2. `mid/current` をその一意名へ `ln -sfn` する。
3. JBoss を起動する。

修正前は、JBoss が開くパスが `standalone/log` → `current` → 一意名、である。ディレクトリは空なので、ハンドラは新しい `server.log` を作成する。`lastModified` は今なので、次の境目は「次の日の 0 時」になる。この JVM は、次の境目まで自分からは rename しない。

FD は、作成した実体を指す。ファイル名が後から変わっても、この FD は同じ実体に書く。ハンドラはパスが付け替わったことを見にいかない。次にパスを使うのは、自分の次の境目（通常は翌日）である。それまで、FD の先の実体がどの名前でディレクトリに載っていても、ログはその実体に増える。

したがって、誰かがこの `server.log` を `server.log.2026-09-16` へ rename すると、新しいタスクのその日のログはすべて前日付の名前のファイルに入る。`server.log` という名前の新しいファイルが隣に出来ても、新しいタスクはそれを開かない。

## 6. 日付の境目と 100% / 200% が重なったときの絵

前提: JVM のタイムゾーンで 2026-09-17 0:00 が境目。デプロイは境目の前に始まり、新しいタスクのエントリポイントが `current` を向け替えたあとも、古いタスクはドレイン中で生きている。日中に起動して夜を越す場合も、境目の瞬間の絵は同じである。

| 順番 | 古いタスク | 共有 `current` | 新しいタスク | ディスク上の見え方 |
|---|---|---|---|---|
| 1. 9/16 の稼働中 | FD-A が `旧/server.log`（実体 A） | 旧ディレクトリ | まだいない | 旧の `server.log` が伸びる |
| 2. 新しいタスクが起動 | FD-A はそのまま | **新ディレクトリへ向け替え** | `新/server.log`（実体 B）を作り FD-B を得る。次の境目は 9/18 0:00 | それぞれの `server.log` が伸びる。この時点では正しい |
| 3. 9/17 0:00 以降の古いタスクの最初のログ | 自分の FD-A を閉じる。パス経由で rename と reopen | 新ディレクトリのまま | FD-B は実体 B を持ったまま | rename の対象は `新/server.log` |
| 4. rename の結果 | 開き直したパスに実体 C の `新/server.log` を作り、以降そこへ書く | 新ディレクトリ | 実体 B の名前は `新/server.log.2026-09-16`。FD-B はそこへ書き続ける | 新しい日のログが前日付ファイルに増える |
| 5. 古いタスクが止まる | FD を閉じて終了 | 新ディレクトリのまま | FD-B は日付が変わるまで実体 B のまま | `current` の先では、前日付ファイルが当日ログに見える |

`current/server.log` を見ていると、中身は古いタスクが境目のあとに書いた分である。`current/server.log.2026-09-16` を見ていると、中身は新しいタスクのログである。名前と中身の日付が逆に見える。

境目より**前**に古いタスクが rollover を終えてから新しいタスクが起動した場合は、rename は古いディレクトリの中で終わる。その回は事故にならない。事故になるのは「`current` が新しいディレクトリを指した状態で、古いタスクの rollover が走る」順である。ドレインが数分続くデプロイでは、この順が普通に起きる。

`Files.move` は `REPLACE_EXISTING` である。向け先に同じ日付のファイルが既にあると、移動がそれを置き換える。新しいディレクトリは通常は空なので、最初の事故は「置き換え」ではなく「名前の付け替え」である。

## 7. 日中と夕方にタスクが複数になるとき

日中のデプロイも、夕方のデプロイも、タスクの重なり方は 100/200 で同じである。

境目より前は、古いタスクのハンドラは rename しない。FD は起動時に開いた実体を指し続ける。新しいタスクは自分のディレクトリに `server.log` を作る。ログはタスクごとに分かれる。

この状態のまま夜を越すと、第 6 節の 3 行目が夜中に起きる。日中に「問題なく見えていた」複数タスクが、日付の境目で前日付ファイルへの追記に変わる。

希望台数が最初から 2 以上で、両方のタスクが日付をまたいで生きる場合も同じである。`current` を最後に向け替えたタスクのディレクトリが、他の生き残っているタスクの rollover の rename 先になる。

時間単位の suffix（`.yyyy-MM-dd-HH`）にしている場合、同じ付け替えが**毎時**起きる。日中の重なりでも、次の時の境目で前の時間のファイルへ書き続ける。

---

## 8. JBoss を起動し直したとき、ファイル名はどうなるか

「起動する」には種類がある。種類ごとに、出来るファイルが違う。

### 8.1 コンテナごと起動し直す（timestamp 方式。修正後の既定）

エントリポイントが毎回新しいディレクトリを作る。中は空である。

- 出来るのは `server.log` だけである。
- 前のディレクトリの `server.log` は、書いたプロセスがもういないので、誰も rename しない。名前は `server.log` のまま残る。日付が変わっていても `server.log.2026-09-16` にはならない。
- `server.log.yyyy-MM-dd-HH` も、`server.log-yyyy-MM-dd HH` も、起動だけでは出来ない。

### 8.2 同じディレクトリで、同じ日に起動し直す（taskid 方式で同一タスクのコンテナ再起動、またはプロセスだけ再起動）

`server.log` の最終更新は今日の期間に入っている。次の境目は次の 0 時である。

- rename はしない。
- `append=true` なので、既存の `server.log` の末尾に続く。
- 起動のたびに日付付きファイルは出来ない。

### 8.3 同じディレクトリで、日付をまたいで起動し直す

プロセスは境目の瞬間にいなかったので、境目ちょうどでの rollover は無い。ディスクには昨日の内容を持った `server.log` が残っている。

起動後の最初のログ行で、ハンドラは最終更新時刻から「境目を過ぎている」と判断する。

1. その `server.log` を `server.log.2026-09-16` へ rename する（自分のディレクトリの中）。
2. 新しい `server.log` を開く。
3. 今日の行は新しい `server.log` に入る。

これは正しい日次ローテーションである。前日付ファイルへ今日の行が入り続ける状態ではない。今日の行が前日付ファイルに入り続けるのは、第 6 節のように**他プロセスの FD が残ったとき**である。

### 8.4 `:reload` や、ログを 1 行も出さない再起動

ハンドラを作り直しただけでは、`setFile` は rename しない。最初のログ行まで名前は変わらない。ログが無ければ、日付をまたいでも `server.log` のままである。

### 8.5 `server.log-yyyy-MM-dd HH` という名前はいつ出るか

標準の suffix `.yyyy-MM-dd` では出ない。起動ごとにも出ない。

出るのは suffix に時の記号（`H` `k` `K` `h`）を入れたときで、名前は `server.log.2026-09-17-00` のように **ドット区切り**になる。パターンに空白を文字として入れたときだけ、ファイル名に空白が入る。EAP の初期設定はそうなっていない。

サイズで回す `size-rotating-file-handler` の名前は `server.log.1` のように番号である。日付も時刻も付かない。

`periodic-size-rotating-file-handler` は、日付の suffix と番号の両方を持ち得る。番号が付く条件は `maxBackupIndex` が 0 より大きいときである。日付の境目の基本動作（パスで rename し、他プロセスの FD は残る）は同じである。

## 9. デプロイ設定だけでは止められない理由

| 設定 | 重なり | 日付の境目に両方生きていると |
|---|---|---|
| minimum 100 / maximum 200 | 新しいタスクを先に起動する。無停止に必要 | 古いタスクの rollover が共有 `current` を辿ると事故になる |
| minimum 0 / maximum 100 | 古いタスクを止めてから新しいタスクを起動する。そのあいだは台数が減る | 登録解除と `stopTimeout` が境目をまたげば、同じ rename が残る |
| 希望台数 2 以上を常時維持 | デプロイしていなくても複数が生きる | 毎夜、最後に `current` を向けたディレクトリが rename の的になる |
| デプロイ時刻を昼にする | 昼の時点では rename しない | そのタスクが夜を越せば、夜に同じ事故になる |

100/200 は無停止のための設定として残してよい。事故の原因は比率ではなく、rollover が共有の札を辿ることである。

## 10. 今回の実装が止めるもの

JBoss が開くパスと、rollover が rename するパスを、起動時の実ディレクトリに固定する。`current` は案内札として更新し続ける。

### 10.1 コンテナの中の個人の札

イメージのリンクを次に変えた（`docker/front/Dockerfile` と `docker/back/Dockerfile`）。

```
/opt/jboss-eap/standalone/log  →  tmp/jboss-log-target     （相対リンク。ビルド時に確定）
```

エントリポイントは、タスクローカルな `standalone/tmp` の上に次を作る。

```
standalone/tmp/jboss-log-target  →  /mnt/logs/.../mid/<この起動の一意名>
```

`tmp` はタスクごとに別のボリュームである。他のタスクが EFS の `current` を向け替えても、このリンクは動かない。追加のボリューム定義は要らない。`tmp` はもともと JBoss の起動に必須である。

これは、検討メモの案 D（コンテナローカルな間接リンク）を、新しいマウントポイントを増やさずに置いた形である。

### 10.2 JVM に渡す実ディレクトリ

エントリポイントは `JBOSS_LOG_DIR` に実ディレクトリの絶対パスを入れてから `standalone.sh` を起動する。`standalone.sh` は、この値が空でなければそれを使い、次の両方に展開する。

- `-Djboss.server.log.dir` … ロギングサブシステムの `server.log`
- `-Dorg.jboss.boot.log.file` … ブート時の `logging.properties` が開くファイル

ハンドラが覚える `File` は実ディレクトリ配下になる。rollover の `Files.move` は `current` を辿らない。

`JAVA_OPTS` には足さない。`standalone.conf` は `JAVA_OPTS` が最初から入っていると、既定のヒープ設定を足さない。ディレクトリの指定は `JBOSS_LOG_DIR` だけで足りる。

これは検討メモの案 C である。シンボリックリンクの要件は 10.1 が満たすので、`standalone/log` というパスも残る。

### 10.3 タスク ID 方式

`LOG_ID_MODE=taskid` で、ディレクトリ名が ECS タスク ID になる。取得できないとき、およびタスク ID にディレクトリ名として使えない文字があるときは、timestamp 方式へ戻して警告する。実装は `entrypoint.sh` にあり、configuration の復元とパスの固定も行う。

`entrypoint.taskid.sh` は、`LOG_ID_MODE=taskid` をセットして `efs-entrypoint.sh` を呼ぶラッパーである。以前の「中身が古い単体スクリプト」は使わない。ラッパーを `efs-entrypoint.sh` という名前で上書きすると、呼び先が自分になるので起動を拒否する。

使い方は次のどちらかである。

- タスク定義の環境変数に `LOG_ID_MODE=taskid` を足し、ENTRYPOINT は `efs-entrypoint.sh` のままにする。
- ENTRYPOINT を `/usr/local/bin/efs-entrypoint-taskid.sh` にする。

同一タスクの中でコンテナだけ再起動したときは、同じタスク ID のディレクトリを再利用する。日付をまたいでいれば、第 8.3 節の正規のローテーションが**そのディレクトリの中だけ**で起きる。

### 10.4 古いイメージのまま base だけ更新したとき

`standalone/log` がまだ `mid/current` を指しているイメージでは、エントリポイントは警告を出して起動する。`standalone.sh` は `JBOSS_LOG_DIR` の実ディレクトリへ書くので、標準の起動コマンドでは同じ事故は起きない。

`LOG_LINK_STRICT=1` にすると、共有 `current` を指したイメージでは起動しない。front / back を再ビルドしたあとに使う。

`standalone/log` をパスとして開く独自スクリプトは、イメージを再ビルドするまで `current` を辿る。再ビルド後は `tmp/jboss-log-target` を辿る。

### 10.5 修正後の同じタイムライン

| 順番 | 古いタスク | 新しいタスク |
|---|---|---|
| 起動 | 自分の実ディレクトリの `server.log` に FD を持つ | 別の実ディレクトリの `server.log` に FD を持つ |
| `current` の向け替え | 自分のパスは動かない | 自分のパスは動かない |
| 日付の境目 | 自分のディレクトリで `server.log` → `server.log.yyyy-MM-dd` とし、新しい `server.log` を開く | FD は自分の `server.log` のまま。次の境目まで自分は rename しない |
| 見えるファイル | 昨日の内容は日付付き、今日の内容は `server.log` | 今日の内容は `server.log`。前日付ファイルは出来ない |

## 11. 運用で残る注意

- **タイムゾーン。** 境目は JVM のタイムゾーンの 0 時である。イメージが UTC のままなら、日本時間の 9:00 に回る。業務日の 0:00 に回すなら、コンテナの `TZ=Asia/Tokyo` と JVM のタイムゾーンを日本にする。今回の修正はパスの固定であり、タイムゾーンは変えていない。
- **1 ファイルにハンドラは 1 つ。** 同じ `server.log` を 2 つのハンドラが開くと、片方が rename したあとも、もう片方の FD が日付付きの名前へ書き続ける。これはタスクが 1 つでも起きる。`logging.properties` と `standalone.xml` で、`server.log` を開く periodic ハンドラは 1 つにする。
- **`standalone.conf` で `JBOSS_LOG_DIR` を `current` に戻さない。** 戻すと、プロパティ側の固定が外れる。個人のリンク（10.1）は残る。
- **`standalone/tmp` を起動後に空にしない。** 空にすると `jboss-log-target` が消える。`JBOSS_LOG_DIR` で既に開いたハンドラは実パスを覚えているので書き続けられる。あとから `standalone/log` を開く処理は、リンクが無いと失敗する。
- **アプリログは別である。** `/webapp/.../logs` はサービスごとの共有ディレクトリのままである。今回の固定は JBoss の `server.log` 向けである。
- **既に動いているタスク。** 修正は次の起動から効く。デプロイでタスクを入れ替えるまで、古い経路のタスクは残る。
- **`current` の見方。** 案内札なので、重なっているあいだに `current/server.log` を見ると「最後に起動したタスク」だけが見える。前のタスクのログは `mid/<そのタスクの一意名>/` にある。
- **古いディレクトリの掃除。** `mid/` は起動のたびに増える。これは修正前からの性質である。

## 12. 確認したこと

`docker/base/tests/rotation_isolation_test.sh` を Linux コンテナ（`python:3.12-alpine`）で実行し、通過した。JBoss 本体は起動していない。再現しているのは、ハンドラと同じ 3 手（FD を閉じる、パスで rename する、パスで開き直す）と、エントリポイントのパス固定である。

| 試験 | 結果 |
|---|---|
| 共有 `current` を辿る rollover | 新しいタスクの追記は `server.log.2026-09-16` に入る。開き直した `server.log` には古いタスクの行が入る |
| コンテナごとの `tmp/jboss-log-target` | 新しいタスクの追記は `server.log` に残る。日付付きファイルは古いディレクトリにだけ出来る |
| 旧イメージのリンク + `JBOSS_LOG_DIR` | `current` を向け替えても、実ディレクトリの FD と rename はそちらに残る |
| エントリポイント（新しいリンク） | `JBOSS_LOG_DIR` は実ディレクトリ。`current` を向け替えても `standalone/log` の解決先は動かない。既存の `JAVA_OPTS` は変わらない |
| エントリポイント（旧リンク） | 警告を出して起動し、`JBOSS_LOG_DIR` は起動時の実ディレクトリのまま |
| `LOG_LINK_STRICT=1` | 共有 `current` のイメージは起動しない |
| `LOG_ID_MODE=taskid` | ディレクトリ名はメタデータのタスク ID。同じ ID の再起動は同じディレクトリ。ドットを含む ID は timestamp へ戻す |
| ラッパー | `efs-entrypoint-taskid.sh` は taskid モードで本実装を呼ぶ。`efs-entrypoint.sh` という名前で置くと起動しない |

EFS 上の実タスクと、実物の JBoss EAP プロセスでの夜間デプロイは、この作業環境では実行していない。上の試験が固定しているのは、事故の機構（パスの辿り直しと、残った FD）と、エントリポイントがそのパスを実ディレクトリに固定することである。
