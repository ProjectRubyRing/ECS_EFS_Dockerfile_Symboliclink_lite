# JBoss EAP ログのタスクごと分離 — 検討した実装案と不採用理由

`/opt/jboss-eap/standalone/log` を「ECS タスク ID (またはそれに代わる一意な名前)」の
ディレクトリへ紐付けたい。しかし前提条件が互いに衝突する:

- シンボリックリンクは **ルート FS 上**にあるため、`readonlyRootFilesystem=true` では
  **イメージビルド時にしか作成できない**。
- ECS タスク ID は **タスク起動時に採番**されるため、**ビルド時には存在しない**。
- 同一イメージから多数のタスクが起動されるため、「ビルド時に確定する値」は
  そのままでは「タスクごとに異なる値」になり得ない。

この衝突をどう解くかで 5 案を比較した。ディレクトリの分離は **案 A'**
(起動時刻-ランダム8桁。タスク ID が必要なら `LOG_ID_MODE=taskid`) を使う。
開く経路は、当初の「共有 `current` を 2 段目にする」形から、
**案 C の `JBOSS_LOG_DIR` と、案 D のコンテナローカルリンクを既存の `standalone/tmp` に置く形**
へ寄せた。追加のタスク定義ボリュームは要らない。
`current` は案内札として残す。日付またぎの動作は
[`SERVER_LOG_DATE_ROLLOVER.md`](./SERVER_LOG_DATE_ROLLOVER.md) を参照。

---

## 案 A: EFS 上の `current` リンクを起動時に張り替える 2 段リンク方式 (タスク ID 名) 【保管】

### 仕組み

- ビルド時: `/opt/jboss-eap/standalone/log → /mnt/logs/<コンテナ名>/logs/<サービス名>/mid/current`
  という固定リンクをルート FS に焼き込む (タスク ID を含まないので確定できる)。
- 起動時: エントリポイントがメタデータエンドポイント v4 からタスク ID を取得し、
  EFS 上に `mid/<タスクID>/` を作成、EFS 上のリンク `mid/current` を
  `ln -sfn` で張り替える。EFS は readonlyRootFilesystem の対象外なので書ける。
- 取得失敗時は `起動時刻-ランダム値` の代替名で同じ一意性を確保する。

### メリット

- ルート FS への起動後書き込みが完全にゼロ。`readonlyRootFilesystem=true` と完全に両立。
- 本物の ECS タスク ID がディレクトリ名になるため、CloudWatch や `aws ecs describe-tasks`
  の情報とログを突き合わせられる (運用調査で最も価値が高い)。
- タスク定義の変更が不要 (追加ボリュームも追加設定も要らない)。
- JBoss 側の設定 (standalone.xml) を一切触らない。ミドルウェアのバージョンアップに強い。
- 過去タスクのログは EFS 上に自動的に残り、要件の「前のタスクのログとの一意性維持」を満たす。

### デメリット

- リンクが 2 段になるぶん、初見の人には構成の理解コストがある (本ドキュメントで補う)。
- 同一サービスのタスクが**常時複数**並走する場合、`current` は「最後に起動したタスク」
  を指すため、先行タスクのログローテーション新規ファイルが後発側ディレクトリに
  混ざり得る (open 済みハンドルは影響なし)。desiredCount=1 運用なら実害はない。
- `mid/` 配下にタスクごとのディレクトリが蓄積するため、掃除の仕組みが別途必要。

## 案 A': 名前を「起動時刻-ランダム8桁」で自前生成する 【ディレクトリ名として採用】

案 A の共有 `current` を開く経路はそのままに、**張り替え先ディレクトリの
名前だけを ECS タスク ID から「起動時刻(YYYYMMDDhhmmss)-ランダム英数字8桁」に
差し替えた**変種。ディレクトリ名の既定は今もこれである。
開く経路は、日付またぎの事故のあと `JBOSS_LOG_DIR` と `tmp/jboss-log-target` に
分離した。タスク ID を名前にするときは同じ `entrypoint.sh` を `LOG_ID_MODE=taskid`
で起動する。`entrypoint.taskid.sh` はそのラッパーである。

### 仕組み

- ビルド時: 案 A と完全に同一 (`…/mid/current` への固定リンク)。
- 起動時: エントリポイントがコンテナ内で
  `date +%Y%m%d%H%M%S` + `-` + `ランダム英数字8桁` を生成して `mid/<一意名>/` を作り、
  `current` を張り替える。ランダム 8 桁は `/dev/urandom` を最優先に生成し、
  `uuid` → `awk 乱数` へ多段フォールバックする。生成直後に `mkdir` で実在チェックし、
  万一衝突したら引き直す (`mkdir` は原子的なので同時起動でも 1 つだけ成功)。

### メリット

- 案 A のメリット (readonlyRootFilesystem 両立、過去ログ残存、タスク定義非変更、
  JBoss 無改修) をそのまま継承する。
- **ECS メタデータエンドポイントに一切依存しない。** ローカル `docker run` でも
  クラウド ECS でも挙動が同じで、メタデータ無効化・遅延・IAM/ネットワーク要因での
  取得失敗といった不確定要素が消える (案 A では毎回の HTTP 取得が必要だった)。
- 複数の ECS サービス・複数タスクが同一 EFS を共有しても、秒精度タイムスタンプ +
  高エントロピー 8 桁 + `mkdir` 原子性で一意性を担保できる。
- 接頭辞が起動時刻なので、ディレクトリ名だけで新旧の並べ替え・世代削除がしやすい。

### デメリット

- ディレクトリ名が **本物の ECS タスク ID ではない**ため、`aws ecs describe-tasks` や
  CloudWatch のタスク ID と機械的に突き合わせできない (起動時刻での照合になる)。
  タスク ID 突合せが必要なら `LOG_ID_MODE=taskid` にする。
- `mid/` 配下のディレクトリ蓄積は残る。掃除は従来どおり必要。
- 共有 `current` を open / rename の経路に使う構成は、日付をまたぐ並行タスクで
  `server.log.yyyy-MM-dd` へ書き続ける。現行の entrypoint はその経路を使わない。

### 判定

ディレクトリ名は、この自前生成を既定にする。
タスク ID で突合せたいときは `LOG_ID_MODE=taskid` を渡す。
`COPY` 対象を古い単体スクリプトへ差し替える手順は使わない。
開く経路の分離は文書先頭の追記と `SERVER_LOG_DATE_ROLLOVER.md` を参照。

## 案 B: ビルド時に UUID / ビルド番号 / Git SHA を生成して焼き込む 【不採用】

### 仕組み

Dockerfile 内で `RUN cat /proc/sys/kernel/random/uuid > /etc/build-id` のように
ビルド時に一意値を生成し、
`/opt/jboss-eap/standalone/log → …/mid/<ビルド時UUID>` を直接焼き込む。
起動時処理は「ディレクトリの mkdir」だけで済む。

### メリット

- 実装が最も単純。エントリポイントでのメタデータ取得もリンク張り替えも不要。
- 「Dockerfile ビルド時に生成できる値」という点では要件の文言に最も忠実。
- リンクは 1 段で、パス解決の理解が容易。

### デメリット (不採用の決定的理由)

- **一意性の単位が「イメージ」であって「タスク」ではない。**
  同じイメージからタスクが再起動・スケールアウトすると、**全タスクが同じ
  ディレクトリに書き込む**。「タスクが切り替わって起動したとき、前のタスクの
  ログと一意性を維持する」という要件そのものを満たせない。
  タスクはデプロイなしでも入れ替わる (ヘルスチェック失敗、ホスト障害、
  スポット中断、AZ リバランス等) ため、この欠陥は日常的に顕在化する。
- ビルド時に生成できる値 (UUID、タイムスタンプ、Git SHA、CI ビルド番号) は
  すべて「そのイメージの全タスクで共通」という性質から逃れられない。
  つまり**この方式の枠内にはタスク ID の代わりになれる値が原理的に存在しない**。
  これが本案を不採用にした核心である。
- ログとタスクの対応が取れず、障害調査で「どのタスクのログか」を特定できない。

### 判定

要件の核心 (タスク切替ごとの一意性) を満たさないため不採用。
「ビルド時に生成できる値でタスクごとの一意性を出せるか」という問いへの答えは
**「原理的に不可能」**であり、だからこそ「ビルド時に固定できるのはリンクの
入口だけにして、一意性は EFS 側 (起動時に書ける場所) で実現する」案 A に倒した。

## 案 C: JBoss の起動引数 `-Djboss.server.log.dir` でログ先を直接指定 【不採用 (次点)】

### 仕組み

シンボリックリンクを使わず、エントリポイントがタスク ID を取得した上で
`standalone.sh -Djboss.server.log.dir=/mnt/logs/<コンテナ名>/logs/<サービス名>/mid/<タスクID>`
のように JBoss 標準のシステムプロパティでログディレクトリそのものを差し替える。

### メリット

- リンクを一切使わないため、案 A の並行タスク時の `current` 競合が**完全に消える**。
  各タスクが自分のディレクトリを直接指すので、desiredCount>1 でも厳密に分離できる。
- `jboss.server.log.dir` は JBoss EAP の公式なプロパティで、挙動が保証されている。
- readonlyRootFilesystem とも完全に両立 (ルート FS に何も作らない)。

### デメリット (不採用の理由)

- 「`/opt/jboss-eap/standalone/log` **シンボリックリンクを作成して**紐付ける」
  という本件の明示要件から外れる。運用手順書・監視設定が
  `/opt/jboss-eap/standalone/log` を参照している場合、そのパスに実体が無くなる。
- 起動スクリプトの引数組み立てに手を入れるため、standalone.conf や
  ラッパースクリプトの管理が増える。JBoss の起動系をいじりたくない場合は不向き。
- アプリログ (`/webapp/...logs`) と pdf のリンクは結局必要なので、
  リンク方式と JVM プロパティ方式が混在し、仕組みが 2 系統になる。

### 判定

技術的には最も筋が良く、**将来 desiredCount>1 の厳密分離が必要になったら
この案へ移行することを推奨**する。今回は「シンボリックリンクで実現する」
という要件を優先し不採用とした (案 A に `-D` を追加するだけで移行可能)。

## 案 D: エフェメラルストレージの書き込み可能ボリュームを間接リンク置き場にする 【不採用】

### 仕組み

タスク定義にホストパス無しのボリューム (Fargate ならエフェメラルストレージ、
EC2 なら Docker ボリューム) を定義し、例えば `/var/linkfarm` にマウントする。
readonlyRootFilesystem=true でも**マウントされたボリュームは書き込み可能**。

- ビルド時: `/opt/jboss-eap/standalone/log → /var/linkfarm/jboss-log` を焼き込む。
- 起動時: エントリポイントが `/var/linkfarm/jboss-log → /mnt/logs/.../mid/<タスクID>`
  というリンクを**コンテナローカルの書き込み可能領域**に作成する。

### メリット

- 間接リンクが**コンテナごとに独立**しているため、案 A の弱点である
  並行タスク時の `current` 競合が発生しない。EFS 上には共有の可変リンクを置かない。
- 本物のタスク ID を使える点は案 A と同じ。
- 「シンボリックリンクで紐付ける」という要件の形も保てる。

### デメリット (不採用の理由)

- **タスク定義の変更が必要** (volumes / mountPoints の追加)。今回の変更範囲を
  「Dockerfile とエントリポイント」に収めるという前提を超える。
  4 サービス × フロント/バック分のタスク定義すべてに追加修正が波及する。
- コンテナ内のリンク段数・登場する場所が「ルート FS → エフェメラルボリューム → EFS」
  の 3 層になり、構成の説明コストが 5 案中で最も高い。
- エフェメラルボリュームはタスク終了で消えるため、`linkfarm` の中身は
  デバッグ時に事後確認できない (EFS 側の実体は残るので致命的ではない)。

### 判定

並行タスク要件が出た場合の有力な代替 (案 C と並ぶ次点)。
今回はタスク定義非変更・構成の単純さを優先し不採用。

## 案 E: 単一イメージ + 起動時に環境変数でリンクを組み立てる 【不採用】

### 仕組み

サービス名・コンポーネント名をビルド時に焼き込まず、単一イメージを全サービスで
共有する。起動時にタスク定義の環境変数 (`Service_Name` / `Component_name`) や
メタデータエンドポイントの `ServiceName` を読み、エントリポイントが
`/webapp/.../logs` などのシンボリックリンク自体を起動時に作成する。

### メリット

- イメージが 1 つ (front/back で 2 つ) で済み、ECR 管理・ビルド時間・
  デプロイパイプラインが大幅に簡素化される。
- サービス追加時にイメージの再ビルドが不要 (タスク定義の環境変数だけで完結)。

### デメリット (不採用の決定的理由)

- リンクを起動時にルート FS へ作る必要があり、**`readonlyRootFilesystem=true` と
  真っ向から矛盾する**。回避するにはリンク置き場をすべて書き込み可能ボリューム化する
  (案 D の全面適用) 必要があり、`/webapp/webapp9mf02` 直下や
  `/opt/jboss-eap/standalone` 直下をボリュームにするのはアプリ資材の配置と衝突する。
- 「ビルド時にシンボリックリンクを作成する」という本件の明示要件に反する。
- 起動時の環境変数設定ミスがそのまま実行時障害になる (ビルド時なら CI で検出できる)。

### 判定

readonlyRootFilesystem 要件と両立しないため不採用。
イメージ数の増加 (最大 8) は CI のマトリクスビルドで吸収する。

## 比較まとめ

| 案 | 起動ごとの一意性 | readonly RootFS 両立 | 本物のタスクID | メタデータ非依存 | 並行タスク分離 | タスク定義変更 | 実装/理解コスト | 判定 |
|----|----|----|----|----|----|----|----|----|
| A: 共有 current を open 経路にするタスクID | ○ | ○ | ○ | × | × (日付またぎで混線) | 不要 | 低〜中 | 廃止 (経路が危険) |
| A': 共有 current を open 経路にする timestamp | ○ | ○ | × | ○ | × (日付またぎで混線) | 不要 | 低〜中 | 名前生成だけ採用 |
| B: ビルド時 UUID 焼き込み | **× (イメージ単位)** | ○ | × | ○ | × | 不要 | 最低 | 不採用 |
| C: jboss.server.log.dir | ○ | ○ | 任意 | 任意 | **○** | 不要 | 中 | **採用 (JBOSS_LOG_DIR)** |
| D: コンテナローカル間接リンク | ○ | ○ | 任意 | 任意 | **○** | 追加ボリュームは不要 (既存 tmp) | 中 | **採用 (tmp/jboss-log-target)** |
| E: 単一イメージ + 起動時リンク | ○ | **×** | ○ | ○ | △ | 不要 | 中 | 不採用 |

**採用理由の要約**: ディレクトリ名は案 A' (既定) または案 A のタスク ID
(`LOG_ID_MODE=taskid`、実装は entrypoint.sh に統合)。
開く経路は案 C と案 D を組み合わせ、共有 `current` を rename の対象から外した。
案 D が当初不要とした「新しいボリューム」は、既に必須の `standalone/tmp` を
リンクの置き場にすることで避けている。案 B と案 E は不採用のまま。
